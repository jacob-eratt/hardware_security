# Results — 2026-11-25

Everything done on 2026-11-25, continuing `HANDOFF_2026-11-24.md`. Read `architecture_spec.md` for the design. All numbers are on independent test sets (seed 2 or later; training used seed 1), and models were selected on val, free-running, unless marked **val**. Nothing from today is committed yet.

**Metric reminder:**
- **acc** = per-access hit/miss accuracy.
- **contents exact-stream** = the fraction of streams where the model's predicted contents of the accessed set are right after *every* access. One wrong eviction anywhere fails the whole stream. This is the headline metric, because it shows whether the policy itself was learned, not just whether predictions are good.

## 1. Hardware: recipe C on the Celeron v2 streams (handoff step 7, provisional)

The Celeron was not available, so this uses the existing v2 streams (100k train, 8k independent test). Run: `cache-policy-learning/runs/hw_celeron_capC` (`--use-ages --conf-weight`, 15 epochs, seed 1234).

| Model | Test acc | Best val acc | Params | Test log-loss |
|---|---|---|---|---|
| Three-unit model, recipe C | **0.9795** | 0.9793 | 30,593 | 0.302 |
| Plain GRU (`runs/hit_celeron_v2`) | 0.9706 | 0.9709 | 618,785 | 0.076 |

- It plateaus from about epoch 3. There are about 53 inconsistent steps per epoch out of 5.75M accesses, meaning the hit/miss labels occasionally contradict any possible eviction; these are probably hardware noise.
- **The log-loss is worse** because the model's predictions are hard 0/1, with no confidence. A calibrated confidence output is an open item.

**Val error analysis** (`cache-policy-learning/scripts/hw_val_errors.py`, val split only):
- 0 errors before evictions start and 0 on first touches, so the sets really start empty after the flush.
- Errors concentrate at reuse distance 12–17, near the capacity boundary.
- Accesses where the model's confidence is ≥ 0.99 (95% of all) have 0.6% error, and 71% of the errors fall in the other 5%.
- **Evidence of L1 filtering (spec §10.3):** lines whose previous access probably hit in L1 (Goldmont L1D is 6-way, so reuse distance ≤ 5) have a lower L2 hit rate. At reuse distance 12–14 it is 0.82 vs 0.92; at 15 it is 0.58 vs 0.81. L1 hits don't update L2 recency, so the line ages the model is given are wrong for those lines. This is a likely source of the remaining error.

## 4. Multi-set and DRRIP set dueling (handoff step 4)

### New code (all with tests)

- **`hardware_security_project/src/cpl/policies/multiset.py`**
  - `MultiSetCache`: one copy of any policy per set.
  - `DRRIPCache`: real set dueling. 32 SRRIP and 32 BRRIP leader sets chosen by complement select; a 10-bit PSEL counter (+1 on an SRRIP-leader miss, −1 on a BRRIP-leader miss); followers use BRRIP when PSEL ≥ 512; BRRIP inserts with priority 2 instead of 3 on 1 in 32 insertions, using a counter shared by the whole cache.
- **`hardware_security_project/src/cpl/data/sim_multiset_dataset.py`**: each stream touches 1–4 random sets out of 1,024, with a 32–96-access sub-stream per set, interleaved. PSEL starts at a random value per stream. Full answer key: contents, evictions, eviction-priority state, set roles, PSEL.
- **`hardware_security_project/tests/test_multiset.py`**: 26 tests against independent reference implementations. Mutation-tested: all 3 planted bugs were caught. The suite has 181 passing tests.
- **Model side (`cache-policy-learning`):**
  - `slot_cache.py`: local set slots, an optional set identity `e(a)` (an embedding of the true set index, standing in for the set decoder), and `--no-global`.
  - `train_hindsight.py`: per-set hindsight constraints, plus the `--no-set-id`, `--no-global` and `--d-set` flags.
  - `train_hits.py` and `eval_sim.py`: per-set baselines and reuse distance.
  - `slot_from_ckpt` / `gru_from_ckpt`: rebuild a model from a checkpoint.
  - `tests/test_multiset_model.py`: sets stay isolated without the global state; hindsight is computed per set, checked exactly against each set's sub-stream (catches a planted cross-set bug); the set identity is wired in. 27 tests pass.
- **Single-set behaviour is unchanged:** the reference runs and the re-grade of old checkpoints reproduce exactly.

### Data

`sim_drrip_ms` and `sim_plru_ms`: 40k streams, seed 1, 37,973 train / 2,027 val. Test sets `*_ms_test`: 8k streams, seed 2. In the DRRIP test set, 93.9% of accesses go to followers, about 3% each to SRRIP and BRRIP leaders, and 54.9% of accesses hit.

### DRRIP result

Run: `runs/sim_drrip_ms_capC` (15 epochs, seed 1234, full model with `e(a)` and `g`). It has 0 inconsistent steps in every epoch, and val plateaued at about 0.938 from epoch 9. Best val 0.9389. Test (`runs/sim_drrip_ms_capC_eval.json`):

| Predictor | acc | reuse dist 0–7 | 8–15 | 16+ | contents acc | contents exact-stream |
|---|---|---|---|---|---|---|
| Three-unit model | **0.9363** | 0.9379 | **0.9184** | **0.7718** | **0.6823** | **0.1299** |
| LRU | 0.8917 | 0.9366 | 0.8558 | 0.5051 | 0.5257 | 0.0159 |
| FIFO | 0.8528 | 0.9079 | 0.7406 | 0.4853 | 0.4501 | 0.0043 |
| random | 0.8552 | 0.9028 | 0.7490 | 0.5030 | 0.4317 | 0.0037 |

A simulator that knows the true PSEL scores 1.0. Guessing a follower's mode wrong makes about 12% of that follower's accesses wrong.

**Diagnosis** (`cache-policy-learning/scripts/drrip_val_diag.py`, val only). The main problem is identifying each set's mode (SRRIP or BRRIP), not executing either rule:
- **SRRIP mode is worse than BRRIP mode:** error 11.3% vs 7.4% on accesses whose line was used before. Followers in SRRIP mode get 34.9% of true misses wrong, even though single-set SRRIP is learned to 0.99.
- **Where streams first go wrong:** 94% of streams' first contents errors are in follower sets, split about evenly between modes. In 57% of them, the model evicted a line at eviction priority 2 while a line at priority 3 existed, so its picture of the priorities was wrong. That is what a wrong guess of the insertion priority (SRRIP inserts at 2, BRRIP at 3) produces. The other 43% are the wrong pick among lines tied at 3.
- **Not the 1-in-32 rule:** 54% of BRRIP-mode first errors happen with no 1-in-32 insertion earlier in that set.
- **Leaders are weak too** (24% of SRRIP-leader misses wrong) even though their mode is fixed, so `e(a)` has not learned which sets are leaders. Each leader set appears in only about 90 training sub-streams.
- The median first error comes halfway through the stream.
- **Open question:** we have not checked whether the mode can be inferred at all from short streams. For part of a stream, the two modes may produce identical hit/miss sequences, so 1.0 may not be reachable by any predictor that doesn't know PSEL.

### Tree-PLRU multi-set (regression check), incomplete

Run: `runs/sim_plru_ms_capC`. Claude Code stopped it at epoch 9 of 15 when memory got low. Val acc was still climbing about 1 point per epoch (0.967 → 0.977). Test on the epoch-9 checkpoint (`runs/sim_plru_ms_capC_ep9_eval.json`):

| Predictor | acc | acc excl. first touch | contents acc | contents exact-stream |
|---|---|---|---|---|
| tree-PLRU (truth check) | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| Three-unit model (epoch 9) | **0.9766** | **0.9645** | **0.7657** | **0.1050** |
| LRU | 0.9382 | 0.9062 | 0.4814 | 0.0047 |
| FIFO | 0.8920 | 0.8360 | 0.4347 | 0.0032 |
| random | 0.8738 | 0.8084 | 0.4313 | 0.0031 |

The same model learns single-set tree-PLRU to 0.998. **So whether the multi-set setup can learn a policy exactly is not yet shown.** This also means the DRRIP gap cannot yet be put down purely to mode identification; part of it may be slower learning in the multi-set setup. One sign favours the mode explanation: DRRIP plateaued by epoch 9 while tree-PLRU was still climbing steeply.
