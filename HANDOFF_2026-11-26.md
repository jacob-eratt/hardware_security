## Observed-outcome prediction (added 2026-11-26, in progress)

**The finding:** in free-running evaluation the model sees only addresses. A DRRIP follower's mode depends on PSEL, whose starting value is random per stream and never shown, and it almost never crosses the threshold within a stream (0.3% of streams). So, from addresses alone, the mode is almost certainly impossible to infer, and the free-running DRRIP number (0.936) may be near its ceiling. The mode-blind ceiling has not been measured yet (next step 5a below). On hardware every outcome is measured, so the realistic task is: predict access t given the true outcomes of the accesses before t.

**New code (tested; `tests/test_observed.py`, 31 model tests pass):**
- `cache-policy-learning/src/cpl/observed.py` (`ObservedChooser`): predicts t from the model's residency, then the true outcome of t corrects residency. A true miss on a held line re-fetches it into the same way; a true hit on a missing line inserts it. The tests check that no prediction depends on the outcome of t or any later access.
- `eval_sim.py --observed`: the model and the baselines (with the same corrections) in observed mode. `--split val` grades one split.
- `train_hindsight.py --observed-train`: the model's own victim choice drives residency, hindsight supplies only the loss, and the same corrections apply. It selects on observed-mode val. `--init-from` fine-tunes a checkpoint.

**Results (val only):** the existing DRRIP checkpoint scores 0.9389 free-running and **0.9530 observed** (+1.4 points). LRU is unchanged at 0.8917, because its correction never alters its state. (`runs/sim_drrip_ms_capC_val{,_observed}.json`)

**In progress at push time:** `runs/sim_drrip_ms_capC_obs`, a 6-epoch `--observed-train` fine-tune from `sim_drrip_ms_capC/best.pt` with `--explore 0`. Epoch 0 had not finished. The laptop slept for about 5 hours mid-run, and observed-mode training is at least 1.3× slower per epoch than normal. The number to beat is 0.9530 observed val. When it finishes, the trainer also scores the test set once, in both modes.

## Next steps

The main goal is to show that the three-unit model can predict an **unknown** cache policy. Steps 1–3 serve that goal directly and are listed cheapest first. Steps 4–6 complete or extend existing work.

1. **Compare the Celeron result against known policies** (minutes, no training, val only).
   - Simulate LRU, tree-PLRU, bit-PLRU, SRRIP and the QLRU variants (the family reported for Intel L2/L3) on the Celeron v2 val streams. Measure each one's agreement with the hardware's hit/miss labels, next to the model's 0.979.
   - **If the model beats every candidate:** it has learned something the textbook policies miss. L1 filtering is a likely cause.
   - **If a candidate scores 0.99 or more:** it is probably the real policy, and the model hasn't found it.
   - Requires: QLRU simulators in `hardware_security_project/src/cpl/policies/`, with tests like the others.
2. **Extract the learned rule from the Celeron model** (about 1 hour of scripting, no training).
   - Feed the trained model hand-made access sequences, like the ones used to reverse-engineer caches, and record which line it evicts.
   - This turns "predicts well" into "learned roughly this rule", which is what identifying an unknown policy means.
3. **Blind simulated test** (about 1–3 hours of training).
   - Train recipe C, with exactly the same settings, on a policy never used in development, for example a QLRU variant.
   - Ideally someone other than the developer picks the policy.
   - If it is learned exactly, the method works on policies it wasn't designed around.
4. **Finish the tree-PLRU multi-set run** (about 3 hours; the command is above).
   - **Done when:** contents exact-stream is close to the single-set 0.998. That shows the multi-set setup can learn a policy exactly.
   - If it can't, the multi-set setup has a problem that must be found before any DRRIP conclusions.
5. **DRRIP, only if multi-set results are needed:**
   - (a) **Mode-blind ceiling** (about 10 minutes, no training): simulate both modes per val stream and measure how often the hit/miss histories can't tell them apart. This gives the real ceiling instead of 1.0.
   - (b) Then the `--no-set-id` and `--no-global` ablations, about 3 hours each, one at a time. They only mean something once the full model gets close to that ceiling.
6. **Still open from the 2026-11-24 list:**
   - mixed-length training for SRRIP's length generalisation;
   - the set decoder (spec §3.1);
   - the bring-up script (spec §7.1);
   - the plain-GRU baselines (spec §6 requires them; the user deprioritised them);
   - modelling L1 filtering in the residency tracker (spec §10.3);
   - a calibrated confidence output (the hardware log-loss is 0.302 vs the GRU's 0.076).
